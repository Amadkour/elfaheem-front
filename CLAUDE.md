# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Flutter education platform (VOD courses, live sessions, attendance, organizations) — package name `flutter_education_app`, Firebase project `elfaheem`, backend at `AppConfig.baseUrl` (`https://nextbrain.site/api`). Targets Android, iOS and Web (web is deployed to Firebase Hosting from `build/web`). Default UI language is Arabic (RTL); English is also supported.

## Commands

```bash
flutter pub get
flutter analyze                      # lints: package:flutter_lints/flutter.yaml; platform dirs are excluded
flutter run                          # add -d chrome for web
flutter test test/org/ test/export/ test/ui/   # the real suites; test/widget_test.dart is the stock counter template and fails
flutter test test/some_test.dart --plain-name "name"   # run a single test
flutter build web && firebase deploy --only hosting
dart run flutter_launcher_icons      # regenerate app icons
dart run flutter_native_splash:create  # regenerate splash screens (android/ios drawables + assets/images/splash*.png)
```

`flutter_webrtc` is overridden to a fork (`github.com/Amadkour/flutter-webrtc`, `main`) in `dependency_overrides`; `screen_protector` is pinned to 1.5.1 on purpose (see the pubspec comment). Don't add the `excel` package: it forces `archive` 3.x, which downgrades `image` and `flutter_launcher_icons`. That's why every Excel/Word file is written by hand on top of `archive` 4. When adding a package, check that `pubspec.lock` gains only that package and nothing gets downgraded.

`EXPORT_SAMPLES=<dir> flutter test test/org/org_export_test.dart` writes `sample.xlsx`, `sample.docx` and `sample.pdf` into `<dir>`, so they can be opened in Office to check how they render.

`test/ui/layout_harness.dart` (`expectNoLayoutErrors`) pumps a widget at 320×640 and 1400×900, in Arabic and English, with `textScaler` 1.3, and fails on any overflow or layout exception. Use it for new widgets: "no overflow on any screen size" is a project requirement. Widgets that need a platform object (LiveKit `Room`, `VideoPlayerController`) get a plain-values presentational widget next to them (`PreJoinLayout`, `LiveControlBar`, `GuestLiveContent`, `vod_player_parts.dart`) and that is what the harness tests.

Dart test gotchas: a record that holds a list never equals another (`expect((a.list, b), …)` fails) — expect the list on its own; the wildcard pattern is `(_, _)`, not `(_, __)` (lint). `AppConfig.lang` is set in `setUp` and flipped inside a test to check both languages.

The code is not `dart format`-ed (formatting `lib/features/org` would rewrite every file). Don't run `dart format` on files you edit: it buries the real change in thousands of lines of re-wrapping.

## Architecture

**Startup (`lib/main.dart`)** — `_bootstrap()` paints a boot splash immediately, runs `_initCore()` (storage, `assets/translation.json`, Firebase, Remote Config, connectivity, offline videos, …) with each step wrapped in `_safe(name, fn, seconds:)` timeouts so one slow service never blocks launch, then runs the real app. Only a storage failure shows `_FatalApp`. Routing is a single `onGenerateRoute: _router` switch over named routes; the initial route comes from `MyAuthProvider.homeRoute`, which maps the user role (`admin`/`super-admin`/`developer` → `/admin_dashboard`, `teacher`, `parent`, `org-admin`/`org-staff` → `/org_dashboard`, but org-staff who manage nothing → `/org_member`, from a cached per-user decision; otherwise student `/dashboard`). An org-admin/org-staff who last left the organization for their personal account starts on `/dashboard` (remembered per user). Offline start-ups route to `/downloads` (or student dashboard + downloads on top).

**Features (`lib/features/<role>/`)** — `student`, `teacher`, `parent`, `admin`, `org`, plus `shared` (attendance, notifications, profile, subscription, downloads, upload, guest, …) and `auth`. Each role has its own dashboard screen.

**State** — `provider` package. All app-wide `ChangeNotifier`s are registered in `lib/core/providers.dart` (`appProviders`); add new global providers there. Feature providers extend `BaseProvider` (`lib/core/base_provider.dart`) and wrap API calls in `run(() => ...)`, which manages `ProviderState` (idle/loading/success/error), sets `errorMessage`, and does one outer retry. Some app-wide state uses singletons (`XService.instance`, `ViewAsState.instance`, `AppConnectivity.instance`).

**Networking (`lib/core/api_client.dart`)** — `ApiClient` is a singleton (`ApiClient()` returns `ApiClient.instance`) on Dio, with `get/post/put/patch/delete/postForm/postMultipart`. Things it does for every request:
- Throws only `ApiException` (`message` is safe to show to the user; `code` holds server codes such as `DEVICE_MISMATCH`, `VIEW_LIMIT_REACHED`). In UI: `ApiException.from(e).message`.
- Retries at the transport level (3 attempts), refreshes tokens, and redirects to login on 401.
- App-layer envelope encryption (X25519 → HKDF → AES-256-GCM, `{"n","ct"}` bodies) and certificate pinning on mobile (`_pinnedCertSha256`). Server cert rotation requires updating the pin list.
- Sends device-ID headers (device binding / blocked-device dialog lives in `features/student/courses/security/`).
- Adds `X-View-As: <id>` while super-admin "view as" mode is active (`utils/widget/view_as_state.dart`).

**Server-driven theme & feature flags** — `ThemeConfigProvider` (`lib/config/theme/`) loads the theme from `GET /api/v1/theme/{platform}` and builds `materialTheme()`. Always read colors via `context.colors`, never hard-coded colors. The same response sets `AppConfig.disableList` (feature kill-switch ids, e.g. `profile.logout`, `teacher_tab_analysis`). To make UI switchable, wrap it in `ParentComponent(featureKey: '...')` (hides it), or give a `BasePage` a `ValueKey('<id>')` (shows a "coming soon" page). `AppConfig.setDisableList` rebuilds the whole widget tree when the list changes.

The disable list has layers. The effective list combines:
- the platform list from the theme response;
- the open organization's list (`AppConfig.setOrgDisableList`);
- `AppConfig.orgEntryKeys`, while the super admin has organizations switched off (`AppConfig.orgsEnabled` / `setOrgsEnabled`, from `orgs_enabled` in the theme response).

A super-admin OFF always wins, because an organization can only add keys. Hidden features disappear rather than greying out. With organizations off, the server answers 403 `orgs_disabled` on org routes, and `/org_dashboard` is wrapped in `OrgsGate`. The theme response's `platform_settings` also sets the platform timezone and 12h/24h (`AppTime.configurePlatform`).

**UI kit** — New screens should use `lib/design/app_kit.dart` (role-neutral aliases over the Data Lab / org / admin widgets: `AppHero`, `AppCard`, `AppStatTile`, `AppEmpty`, `AppListSkeleton` rather than spinners, `AppBanner`, `AppField`, `showAppSheet`, `appConfirm`, …; the header comment of that file has the full usage table) and wrap pages in `BasePage` (`lib/utils/widget/base_page.dart`), which handles the background, kill-switch, and the global upload-progress footer. App-wide rules the kit enforces:
- **Switches:** only `AppSwitch` / `AppSwitchTile` (`app_switch.dart`), never `Switch`/`SwitchListTile`.
- **Dropdowns:** only `AppDropdown`.
- **Displayed times and dates:** always go through `AppTime` (`lib/core/app_time.dart`, re-exported by the kit), which applies the platform or organization timezone and the 12h/24h choice. `AppTime.configureOrg` is set when an organization is opened and cleared when it is left.
- **Table exports:** use `showAppExportSheet(context, AppTableExport)` (`app_table_export.dart`, writers in `lib/design/export/`). It offers Excel, Word and PDF with a column picker, RTL and Arabic fonts, and remembers the last choice per table. Admin `PagedList`s take an `export:` option that fetches every page before exporting.

**Localization** — Strings live in `assets/translation.json` as `{ "key": { "en": "...", "ar": "..." } }`. Use `translate('key')` or `'key'.tr`; a missing key falls back to the key itself. Add both `en` and `ar` for every new key. Current language is `AppConfig.lang` (switched by `LangProvider`); use `pageDirection` for RTL/LTR.

**Offline** — `lib/core/offline/` holds connectivity (one app-wide online/offline answer, wired into `topRouteObserver`) and encrypted offline video downloads (AES-CTR via pointycastle). Offline attendance can relay through a nearby online classmate (`features/shared/attendance/`, `nearby_connections`, Android only).

**Course video player (`lib/features/shared/session/video/`)** — `VideoPlayerScreen(material, playlist:)` is the one player for every caller (session material grid, course profile, downloads); it calls `POST …/materials/{id}/play` itself, plays the encrypted offline copy when `OfflineVideoService.localVariant` has one, and keeps screen protection (`screen_protector`) and wakelock on for the whole visit — switching lectures happens in place (`_openLecture`), never by pushing a second screen. Pure parts (resume logic `VodResume`, `vodPlaylist`/`vodNextOf`, next-up card, lecture list, HUD, captions, skeleton) live in `vod_player_parts.dart` so `test/ui/vod_player_layout_test.dart` can test them without a platform player; the full screen is tested only in its error state with `debugDefaultTargetPlatformOverride = TargetPlatform.iOS` (the Android PiP plugin leaks a timer in tests). Captions are server `.vtt` files (`captions_url`, uploaded by teachers via `POST …/materials/{id}/captions`) and are saved next to offline downloads. On phones swipes change the real screen brightness and media volume (`screen_brightness`, `volume_controller`); elsewhere the player dims/attenuates itself.

**Live room (`lib/features/teacher/sessions/live/`)** — `PreJoinPage(JoinArgs)` → `RoomPage`. The control bar is `widgets/live_control_bar.dart` (presentational, tested) driven by `widgets/controls.dart`; reactions are LiveKit data messages on topic `reaction` (`widgets/live_reactions.dart`). Recording: `sessions.record_enabled` is the creator's switch; `/live-sessions/start` and `/join` return `recording_enabled`, carried as `LiveResponseModel.recordingEnabled` → `RoomPage.recordingEnabled`; when false the teacher's device never starts the client recorder. Guest links: teacher `…/guest-link` routes + public `/api/v1/public/live/{token}` (`lib/features/shared/guest/guest_live_api.dart`, sheet in `teacher/sessions/components/guest_link_sheet.dart`, page `guest_live_page.dart` at route `/live/<token>`, feature key `live.guest_link`). `RoomPage(isGuest: true)` must never call an authenticated API (a 401 redirects to login); `canPublish: false` gives a listen-only bar. Backend: `../back/routers/live_guest_router.py`, `services/live_guest_service.py`, tests `tests/org_v2/e2e_live_guest_link.py`, `e2e_session_record_flag.py`.

**Native code** — Live sessions use LiveKit (`features/teacher/sessions/live/`). Screen recording and screen sharing use platform channels (`com.example.flutter_education_app/native_recorder`, `/radios`). The native side is `android/app/src/main/kotlin/.../ScreenCaptureService.kt` and `MainActivity.kt`, and on iOS `ios/Runner/AppDelegate.swift`, `LocalDebugRecorder.swift`, and the `ios/BroadcastUploadExtension` target. Recordings upload in chunks.

**Organizations (`lib/features/org/`)** — The backend source is next door at `../back` (`routers/organization/`, `services/organization/`). Check payloads there; don't trust the notes alone. Shared logic lives in `org_v3.dart`: `orgCall` keeps `detail.code` and its extras, `orgErrorText` turns codes into bilingual text, and `JoinPolicyDraft` / `ScheduleDraft` build PUT bodies. Several org PUTs replace the whole object (join policy, schedule, room, program, academic settings), so always send every field. The server stores naive UTC: send `orgUtc()` and read `orgParseUtc()`. Org screens use `t(ar, en)` from `admin_common.dart` for inline strings instead of `translation.json`. When you add a server error code, map it in `orgErrorText`. Tests: `flutter test test/org/`.

Entry points by role:
- **Org admins** use `org_dashboard_screen.dart`: sections, with counts from one `GET …/dashboard` call. A department or academic program opens `org_department_dashboard.dart`.
- **Members** get `org_member_dashboard.dart`, which serves members of several organizations, and the unified inbox (`lib/features/shared/inbox/unified_inbox.dart`, `GET /me/inbox`).
- **Mode:** `AppModeController.instance` (`lib/core/app_mode.dart`) holds the Organization/Individual mode and the selected organization. Notification taps that carry `org_id` call `openOrg(id)` before routing. To go back to the personal account use `leaveToPersonal` / `ContextExitButton` (`lib/design/context_switcher.dart`): it clears the org timezone and disable list and pops every org page. Switching the mode alone leaves the org page open. Every org screen needs this exit button.

Other org areas:
- **Joining:** codes and requests, `org_access_joining.dart`, QR scan via `mobile_scanner` in `org_join_scan.dart`, mobile only.
- **Academic levels and prerequisites:** pure logic in `org_levels.dart`, screens in `org_levels_pages.dart`.
- **Announcements with engagement analytics:** `org_announcements.dart`, which includes the embeddable `OrgAnnouncementFeed`.
- **Platform and organization settings:** `admin_platform_*` and `org_platform_settings_page.dart`; the creation fee is in `org_creation_fee.dart`.
- **Join methods:** a unit can offer several at once (automatic, request, code/QR/link, code + request); `JoinPolicyDraft` in `org_v3.dart` keeps the legacy `method` field in sync for older clients.
- **Complaints reports:** `org_reports/` (period → layout designer or uploaded Word/Excel template → PDF/Word/Excel, signature background removal, share in-app or by e-mail; recipients use `OrgReceivedReportsPage`). Backend: `routers/organization/org_reports_router.py`.

**Calendar and meetings (`lib/features/shared/calendar/`)** — Day/week/month views over `GET /me/calendar?start=&end=[&org_id=]`, which merges org timetable slots (already expanded to dated events, with exam pauses applied), exams, meetings and course live sessions. Meetings (private, people, department, department head, course group; online via LiveKit or in person) and invitee answers (accept/decline/propose a time) live in `../back/routers/calendar_router.py` + `services/calendar_service.py` + `data/calendar_models.py`. Creating or moving a meeting answers 409 `attendees_busy` unless sent with `force`. A complaint can be turned into a meeting (`POST /orgs/{o}/complaints/{c}/meeting`). The student/teacher "My schedule" tab reuses this feed for upcoming meetings; a failed meetings load must never fail the tab.

**Course profile (`lib/features/shared/course_profile/`)** — One screen for every role (instructor, TA, creator, student). TAs work on sections/labs only unless the instructor grants more; archived courses are read-only. Backend: `../back/routers/course_profile_router.py` (incl. course announcements), test `tests/org_v2/e2e_course_profile.py`.

Timetables: `OrgScheduleProvider` (`org_providers.dart`) holds the open schedule, its slots, and the conflicts from `GET …/validate`. Its writes send `expected_version`, and a 409 `stale_version` reloads the timetable. The screens are split across these files:
- `org_schedule_hub.dart`: `TimetableJourney` + the next-step banner;
- `org_schedule_pages.dart`: the studio — one toolbar (Generate · Add session · Result & conflicts · Publish, the rest under ⋮), the grid with drag-and-drop (a hard rule blocks the move, a soft one warns), the add/edit form validated live with `dry_run`;
- `org_schedule_grid.dart`: the single filter bar (program/level, instructor, TA, room, group, student) and the grid index; `org_schedule_board.dart`: the wide periods × days board with sticky headers and the session-details dialog;
- `org_schedule_insights.dart`: pre-flight (`GET …/preflight`, `DataHealthCard`), the quality report after a generation, and "why here" for a placed session. Every finding carries `actions[]` — the ranked ways out (`ActionOption`: rank, score 0–100, `auto` = the server applies it, else "by hand"; a manual way is always listed; `best` = the first automatic one). `RankedActions` renders them; Accept posts `…/preflight/accept {key, action_id}` and "Accept every recommended fix" posts `…/preflight/accept-all`. An older server that only sends `action` is turned into one option;
- `org_schedule_remedies.dart`: `GET …/remedies` gives every validator conflict the same ranked `actions` shape (move to a free time, change room, give it to a free colleague, fix the group, unpin, re-solve, override with a reason, …); `RemediesPanel` replaces the plain conflicts list in the Quick Actions sheet; `POST …/remedies/apply` (409 `schedule_conflict` → retry with `force`, 422 `reason_required` for override). Backend: `../back/services/organization/schedule_remedies.py`, `schedule_preflight.py`;
- `org_schedule_reassign.dart`: changing who teaches a session from the slot sheet asks the scope (`askReassignScope`: whole course · this weekly session · one date), dry-runs `POST …/slots/{id}/reassign?dry_run=true` and shows `ReassignCompareSheet` — Before / After with metrics, rank and the moved sessions; apply writes both as revisions and answers 409 `reassign_not_better` unless `force`. Scope "once" writes a one-date occurrence instead. Pin / unpin is `PUT …/slots/{id} {locked}` (`setLocked`). Backend: `schedule_reassign.py`;
- `org_member_changes.dart`, `org_member_today.dart`: one-date changes (substitute · online / offline · cancelled) as `/public/schedule/me` reports them in `changes` and `/me/calendar` applies them; `OccurrenceCard` lets students Accept / Reject and the staff undo; a session's own teacher / assistant taps it on "Today" or in "My timetable" to hold a date online (`switchSessionMode`, students are notified). Backend: `schedule_occurrences.py`, tables `org_schedule_occurrences` / `…_responses`;
- `org_schedule_ical.dart`: the timetable as an `.ics` with weekly RRULEs, built in the app;
- `org_schedule_generate.dart`: the ONE "Generate timetable" action (`complete: true` — strict, then only the rules the admin marks Flexible, until complete or no progress), the live panel, and the result sheet where every broken rule is a proposal to accept or reject (publishing waits: 409 `proposals_pending`). The server also creates and generates a draft per open term by itself (`../back/services/organization/schedule_auto.py`);
- `org_schedule_groups.dart`: students per lecture/lab group, alphabetical / by-ID distribution, moves re-checked for clashes and capacity, roster export;
- `org_schedule_exams.dart`, `org_my_exams.dart`: midterm/final exam timetables and the member's own exams. A published exam window pauses the term's weekly classes (`pause_weekly`). That pause is applied where the app computes today's and the next sessions, because no server route expands weekly slots into dates;
  Generation has a hard 90 s budget: each round's solver only gets the time left, a run no worker started is failed after 2 minutes, and the app stops following after 5 errors or 4 minutes. `completion_pct` is never shown as complete while a session is unplaced, a hard clash remains or a proposal is pending. `QuickActionsPanel` (here, plugged into the studio through `studioQuickActions` in `org_schedule_pages.dart`) uses `GET/POST …/quick-actions[/apply]` (`../back/services/organization/schedule_quick.py`): each action relaxes one locked soft rule with a dry-run impact preview and re-solves only the affected sessions; hard rules answer 422 `rule_locked`;
- `org_schedule_planning.dart`: enrollment estimates and lecture/lab groups;
- `org_schedule_optimizer.dart`: suggestion models and API (shown as last-resort advice in the generation result) and the days/periods horizon;
- `org_schedule_versions.dart`: pure ranking / diff / member-copy logic used by the copies page;
- `org_schedule_copies.dart`: full copies (revisions) and per-member copies, with export;
- `org_schedule_export.dart`: Excel and Word written by hand (SpreadsheetML / WordprocessingML zipped with `archive`) and PDF via `package:pdf` with the bundled Tajawal / Bahij fonts — per teacher / assistant / room / group or one member, merged cells for multi-period sessions, summaries.

Pure logic in those files (`planCourse`, `ScheduleHealth`, `ScheduleHorizon`, `compareVersions`, `diffVersions`, `memberTimetable`, `TimetableGrid`, `TimetableSummary`, `GridFilter`, `GenerationOutcome`, `rulesFlexible`, `PreflightReport`, `RemedyReport`, `ReassignPlan`, `OccurrenceChange`, `orgTodaySessions`) is what gets unit-tested, because `ApiClient` is a singleton and can't be faked.

When a backend route may be missing, call it through an `XxxApi` interface with a `Remote…` and a `Mock…` implementation. The mock is used only with `--dart-define=ORG_SCHEDULING_MOCKS=true` (`kOrgSchedulingMocks`, which is always false in release builds). A missing route is detected with `orgEndpointMissing` (FastAPI's bare 404 "Not Found" or a 405), and the UI then says the feature needs a server update. `docs/backend/scheduling-spec.md` specifies the scheduling backend work (G1–G5 are done in v3.4; G6 is optional). The backend may be changed when the task needs it. Follow `../back/CLAUDE.md`, add tests under `tests/org_v2/`, and record every org API contract change in `../back/FLUTTER_API_CHANGES.md`. The backend tests are standalone e2e scripts. Run them with Python 3.12 and `PYTHONUTF8=1`, for example `PYTHONUTF8=1 ../back/.venv312/Scripts/python ../back/tests/org_v2/e2e_org_v2.py` (or `py -3.12`). The `.venv312` folder is local and git-ignored; plain `python` is not on PATH. There is no Alembic: a new column on an existing org table goes in the column map inside `ensure_org_tables` (`../back/data/models.py`) as well as on the model; a new org table is a model in `../back/data/org_models.py` appended to `ORG_V2_TABLES`, which `ensure_org_tables` creates. The e2e scripts need a database: without a local Postgres, give each run its own `DATABASE_URL="sqlite:///C:/…/x.db"`. Run them on PostgreSQL once before a deploy. Scheduling tests to know: `tests/org_v2/section_count_unit.py` (pre-flight, pure), `e2e_preflight_actions.py`, `e2e_remedies_reassign.py`, `e2e_quick_actions.py`, `e2e_schedule_auto.py`, `e2e_course_plans.py`; the generator needs `ortools` installed.

Registrar (credit-hour and traditional/year systems — registration, waitlists, grades, GPA, attendance denial, degree audit, decisions):
- **App:** `org_registrar.dart` holds pure helpers and code → text maps (`registrarCodeText`, `blockText`, decision kind/risk/action texts, `RegCart`); `org_registrar_member.dart` has the member screens (registration cart, record, teaching/grades, advising, staff consents, my week); `org_registrar_staff.dart` is `OrgRegistrarPage`, the Academics → "registrar" sub-page. A new server code or decision kind needs a label in `org_registrar.dart`.
- **Backend:** `routers/organization/org_registrar_router.py` (staff `/orgs/{id}/registrar`, members `/public/{id}/registrar`) over `services/organization/registrar/`: `policy.py` is pure (rule defaults, GPA, standing, calendar generation, `ruleset(system_type)`), `service.py` does eligibility/registration/grades/audit, `jobs.py` is the hourly tick (`_registrar_tick` in `scheduler_service.py`), plus `allocation.py`, `consent.py`, `traditional.py`. Tables are in `data/registrar_models.py`; new columns on existing tables go in `REGISTRAR_COLUMNS` (no Alembic, `ensure_registrar_tables` adds them).
- **Principles:** every rule is data (`org.settings` rules, inherited from parent orgs, editable in the Rules tab); ambiguous cases never hard-reject but open an `OrgDecision` (with risk, recommendation, alternatives) applied through the `ACTIONS` registry; seats are taken with a conditional UPDATE and waitlist promotion claims rows compare-and-set. Publishing a timetable that puts staff in their unavailable time waits for their consent (409 `staff_consent_pending`) unless an approver forces it with a reason.
- **Tests:** `tests/org_v2/e2e_registrar.py`, `e2e_traditional.py`, `registrar_race.py` (real threads; `RACE_DB_URL=postgresql://…` on an empty database to test Postgres), and `test/org/org_registrar_test.dart`.

**Web** — Code that is not web-safe sits behind `kIsWeb` checks or conditional-import stubs (`url_strategy_stub.dart` / `url_strategy_web.dart`, `web_notification_web.dart` using `package:web`). Do not import `dart:io`-only APIs from code that runs on web without such a guard.

## Agent skills

`.agents/skills/` (tracked in `skills-lock.json`) contains Firebase skills (auth, Crashlytics, Remote Config, Firestore, hosting, security rules, …) and `xcode-project-setup`. Consult them for Firebase or Xcode work.
