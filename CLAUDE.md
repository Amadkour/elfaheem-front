# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Flutter education platform (VOD courses, live sessions, attendance, organizations) — package name `flutter_education_app`, Firebase project `elfaheem`, backend at `AppConfig.baseUrl` (`https://nextbrain.site/api` unless built with `--dart-define=API_BASE_URL=…`; a release build accepts only an `https://` override, see `resolveApiBaseUrl`). Targets Android, iOS and Web (web is deployed to Firebase Hosting from `build/web`). Default UI language is Arabic (RTL); English is also supported.

## Commands

```bash
flutter pub get
flutter analyze --no-fatal-infos --fatal-warnings   # the CI gate (exit 0 = no warnings/errors); lints: package:flutter_lints/flutter.yaml; platform dirs are excluded
flutter run                          # add -d chrome for web
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:18080/api   # Android emulator → local stack (../back/scripts/dev/setup.*, demo accounts in ../back/README.md); web / iOS simulator use http://localhost:18080/api, a USB phone after `adb reverse tcp:18080 tcp:18080`; default is production
flutter test test/org/ test/export/ test/ui/ test/auth/ test/contract/   # the real suites (CI runs them all); test/widget_test.dart is the stock counter template and fails
flutter test test/some_test.dart --plain-name "name"   # run a single test
flutter build web && firebase deploy --only hosting
scripts/build_release.sh apk|appbundle|ipa|web   # release builds (bash): obfuscated, symbols in build/debug-info/<version>/ (keep them: `flutter symbolize -i trace.txt -d build/debug-info/<version>/app.android-arm64.symbols` is the only way to read a stack trace); signing from android/key.properties / env (never committed)
dart run flutter_launcher_icons      # regenerate app icons
dart run flutter_native_splash:create  # regenerate splash screens (android/ios drawables + assets/images/splash*.png)
```

CI (`.github/workflows/ci.yml`, Flutter 3.47.7 stable) runs on pushes to `production`, `main` and `feature/**` and on every pull request — a push to any other branch (e.g. `organizations`) runs nothing until a PR is opened. It gates on: 0 analyzer warnings/errors (plain `flutter analyze` exits 1 on info lints, which are allowed — use the flags above, or count `" warning - "` / `" error - "` lines), the test suites above, `flutter build web --release`, and gitleaks over the tree and the new commits (`.gitleaks.toml`: an allowlist entry must match rule AND path AND value, with a reason).

**API contract test (`test/contract/`)** — scans every path handed to `ApiClient` and checks it against the backend's route snapshot `test/contract/api_paths.json` (`/api/v1/exam/…` against the Exam Engine, `/api/v1/rag/…` against RAG, the rest against the core). After adding a server route, regenerate the snapshot from `../back`: `python scripts/contract/export_api_paths.py --front ../nextbrain-front`. A call the server deliberately lacks goes in `knownMissing` with a reason; the test also fails when an entry is no longer needed. The same export script writes `test/contract/feature_keys.json`, the kill-switch snapshot that `feature_keys_test.dart` checks (see the features guide below).

`flutter_webrtc` is overridden to a fork (`github.com/Amadkour/flutter-webrtc`) in `dependency_overrides`, pinned to a commit `ref:` (change it on purpose, D-010); `screen_protector` is pinned to 1.5.1 on purpose (see the pubspec comment). Don't add the `excel` package: it forces `archive` 3.x, which downgrades `image` and `flutter_launcher_icons`. That's why every Excel/Word file is written by hand on top of `archive` 4. When adding a package, check that `pubspec.lock` gains only that package and nothing gets downgraded.

`EXPORT_SAMPLES=<dir> flutter test test/org/org_export_test.dart` writes `sample.xlsx`, `sample.docx` and `sample.pdf` into `<dir>`, so they can be opened in Office to check how they render.

`test/ui/layout_harness.dart` (`expectNoLayoutErrors`) pumps a widget at 320×640 and 1400×900, in Arabic and English, with `textScaler` 1.3, and fails on any overflow or layout exception. Use it for new widgets: "no overflow on any screen size" is a project requirement. Widgets that need a platform object (LiveKit `Room`, `VideoPlayerController`) get a plain-values presentational widget next to them (`PreJoinLayout`, `LiveControlBar`, `GuestLiveContent`, `vod_player_parts.dart`) and that is what the harness tests.

Dart test gotchas: a record that holds a list never equals another (`expect((a.list, b), …)` fails) — expect the list on its own; the wildcard pattern is `(_, _)`, not `(_, __)` (lint). `AppConfig.lang` is set in `setUp` and flipped inside a test to check both languages.

The code is not `dart format`-ed (formatting `lib/features/org` would rewrite every file). Don't run `dart format` on files you edit: it buries the real change in thousands of lines of re-wrapping. New files are written formatted by hand (D-003).

Docs: `D-nnn` references point to `docs/DECISIONS.md` (design decisions and deliberate deviations; add one when you deviate). `docs/ARCHITECTURE.md` is the long-form architecture, `docs/PROGRESS.md` the phase log of the platform refactor, `TIMETABLE_NOTES.md` the running notes of the timetable rebuild, `docs/AUDIT.md` / `docs/SECURITY_SCAN.md` dated read-only audit reports (their backend halves are in `../back/docs/`), and `documents/` holds developer guides and slides.

## Architecture

**Startup (`lib/main.dart`)** — `_bootstrap()` paints a boot splash immediately, runs `_initCore()` (storage, `assets/translation.json`, Firebase, Remote Config, connectivity, offline videos, …) with each step wrapped in `_safe(name, fn, seconds:)` timeouts so one slow service never blocks launch, then runs the real app. The splash itself is `lib/design/boot_splash.dart` (`BootSplash`, `SplashHandOff`): frame 1 matches the native splash, then the mark floats and tilts in 3D, the tagline from `AppIdentity` appears, and the footer the super admin set ("Powered by …" line + small logo, `splash_footer_*` / `splash_logo_url` on the identity endpoint, edited on the admin Content page, logo bytes cached) shows at the bottom, a greeting with the cached user's first name and a status line driven by `SplashState.instance` (`_safe` reports each step; `SplashPacing` remembers the device's usual boot time to pace the bar); test `test/ui/boot_splash_layout_test.dart`. Only a storage failure shows `_FatalApp`. Routing is a single `onGenerateRoute: _router` switch over named routes; the initial route comes from `MyAuthProvider.homeRoute`, which maps the user role (`admin`/`super-admin`/`developer` → `/admin_dashboard`, `teacher`, `parent`, `org-admin`/`org-staff` → `/org_dashboard`, but org-staff who manage nothing → `/org_member`, from a cached per-user decision; otherwise student `/dashboard`). An org-admin/org-staff who last left the organization for their personal account starts on `/dashboard` (remembered per user). Offline start-ups route to `/downloads` (or student dashboard + downloads on top).

**Features (`lib/features/<role>/`)** — `student`, `teacher`, `parent`, `admin`, `org`, plus `shared` (attendance, notifications, profile, subscription, downloads, upload, guest, calendar, course_profile, exam_engine, rag, inbox, passcode, …), `auth`, and `ads` (`ads_pages.dart`: the home slider, the super admin's ads page with teacher-ad approval, and the teacher's own ads). Each role has its own dashboard screen.

**Home screens and badges** — Every role's home is built from `lib/design/home_kit.dart` (`HomeHeader`, `HomeHeroCard`, `HomeActionGrid`, `HomeAgenda`, `HomeTodoCard`, …; the header comment lists the parts and the 8·16·24·32 rhythm). Badge counts for tabs and sections come from ONE call, `GET /api/v1/me/attention`, kept by `AttentionService.instance` (`lib/core/attention/`): it refreshes every 60 s while in front, on resume, on route change and on silent pushes, and polls only while something listens. Draw a count with `AttentionBadge(tabKey: AttentionTabs.x, orgId:, child:)` (`lib/design/attention_badge.dart`); tapping opens the item's deep link. A new tab key is added in `AttentionTabs` AND in the server's `TABS` (`../back/services/attention_service.py`).

**Navigation glue (`lib/utils/widget/`)** — `AppNavigator` (`app_navigator.dart`) is the one place that opens a "module" from a notification tap, a push, a dialog button or a shared link, always through `navigatorKey` from `main.dart`; add new deep-link targets there rather than in each caller. `DeepLinkService` (`deep_link_service.dart`) handles course share links `https://nextbrain.site/c/<courseId>?ref=<sharerUserId>`, which Flutter's default deep linking feeds to `onGenerateRoute` as `/c/<id>?ref=<uid>`. `VersionCheckService` (`lib/core/version_check_service.dart`) runs once at startup against `GET /app/version-check` and shows a blocking (`must_update`) or dismissible (`should_update`) dialog. The rest of `lib/utils/widget/` is the older widget set (`BasePage`, `ParentComponent`, `PrimaryButton`, `AppBar`, text fields, …) that existing screens still use; new UI comes from `lib/design/` (below), which wraps and re-exports what it needs from there.

**State** — `provider` package. All app-wide `ChangeNotifier`s are registered in `lib/core/providers.dart` (`appProviders`); add new global providers there. Feature providers extend `BaseProvider` (`lib/core/base_provider.dart`) and wrap API calls in `run(() => ...)`, which manages `ProviderState` (idle/loading/success/error), sets `errorMessage`, and does one outer retry. Some app-wide state uses singletons (`XService.instance`, `ViewAsState.instance`, `AppConnectivity.instance`).

**Networking (`lib/core/api_client.dart`)** — `ApiClient` is a singleton (`ApiClient()` returns `ApiClient.instance`) on Dio, with `get/post/put/patch/delete/postForm/postMultipart`. Things it does for every request:
- Throws only `ApiException` (`message` is safe to show to the user; `code` holds server codes such as `DEVICE_MISMATCH`, `VIEW_LIMIT_REACHED`). In UI: `ApiException.from(e).message`.
- Refreshes tokens and redirects to login on 401. Tokens live in `lib/core/token_storage.dart` (secure storage on mobile, SharedPreferences on web); `POST /auth/refresh` sends the refresh token in the body and returns a NEW pair, which is stored (rotation: an old token is dead after one use). `StorageService` keeps only the cached user and UI preferences.
- App-layer envelope encryption (X25519 → HKDF → AES-256-GCM, `{"n","ct"}` bodies) and certificate pinning on mobile (`_pinnedCertSha256`). Server cert rotation requires updating the pin list.
- Sends device-ID headers (device binding / blocked-device dialog lives in `features/student/courses/security/`).
- Adds `X-View-As: <id>` while super-admin "view as" mode is active (`utils/widget/view_as_state.dart`).
- Adds `X-Onboarding-Token` to teacher onboarding routes (`isTeacherOnboardingPath`; token kept in memory by `lib/features/auth/teacher_onboarding_token.dart`), and opens `AdminMfaPage` on 403 `mfa_enrollment_required` (`shouldOpenMfaEnrollment`: never two at once, again only 30 s after the user left it). The settings entry for every role the server allows is `MfaSettingsEntry` (`lib/features/auth/mfa_entry.dart`, feature key `profile.mfa`). Debug request logs go through `redactForLog`: add any new secret field to `logSensitiveKeys`. MFA: `lib/features/auth/mfa.dart` (API + code texts), `mfa_verify_screen.dart` (`openMfaStep`, the login step), `lib/features/admin/admin_mfa_page.dart` (enrolment / status). Every method takes an optional `headers:`.
- Maps 503 `server_busy` (the Exam Engine / RAG in-flight cap) to `ApiMessages.serverBusyAr/En`; coded errors outside org screens get bilingual text in `lib/core/api_error_text.dart` (`apiErrorText`).

Cleartext is refused on devices except `127.0.0.1` / `localhost` (the offline-video loopback server) and `10.0.2.2` (emulator → local stack): `android/app/src/main/res/xml/network_security_config.xml` and iOS `NSAllowsLocalNetworking` (D-010). Every server, media and LiveKit URL must be https / wss.

**Exam Engine and RAG clients (`lib/features/shared/exam_engine/`, `lib/features/shared/rag/`)** — separate backend services (`../back/exam_engine`, `../back/rag_service`) reached through the same `ApiClient` under `/api/v1/exam/…` and `/api/v1/rag/…`. Engine calls go through `engineCall` → `EngineResult`; `unavailable` (bare 404 / 405) means the engine is not routed and the legacy exam flow stays in charge (`engine_exams_section.dart` shows nothing then). Server codes become text via `examCodeText` (exam files) and the RAG files' own maps. Pure, unit-tested parts: `Paper`, `ServerClock`, `AutosaveQueue` (pending answers, `restore()` after an app kill), `EventBuffer`, `PolicyAction` in `exam_taking.dart`; `RagCitation`, `RagAnswer`, `answerRuns` in `rag_chat.dart`. Tests: `test/org/exam_*_test.dart`, `test/org/rag_*_test.dart`. User-facing behaviour of these features is described in `docs/NEW_FEATURES_GUIDE.md`. The exam files follow one pattern: a pure `exam_x.dart` (models, API, code → text, unit-tested) next to an `exam_x_screen.dart` / `_sheet.dart` whose presentational widgets take plain values so the layout harness can pump them. The pieces built on top of the full editor (`exam_authoring.dart`):
- `exam_quick.dart`: the quick exam (Online or Offline first, then questions or one uploaded file, everything else a default under "Advanced"); it builds the same engine objects as the editor (`QuickExam`, `createQuickExam`), and is where exam timetables (`settings.schedule_slot_id`) and "My exams" create exams from.
- `exam_generate.dart`: "Generate the questions for me" — `POST /api/v1/rag/exam-drafts` (202, then polled; 409 `no_course_documents`) lands RAG-written questions in the quick exam as an editable draft.
- `exam_paper.dart` + `exam_paper_pdf.dart` / `exam_paper_docx.dart`: the printable paper (Classic / Modern / Minimal / Auto, or the creator's own Word template with `{{placeholders}}`), paper or answer key, built from the manager's `GET /exams/{id}`. `package:pdf` needs the bundled IBM Plex Sans Arabic (presentation forms that Cairo / Tajawal lack).
- `exam_paper_flow.dart`, `exam_scan_review.dart`: paper exams with scanned answer sheets (bulk scan upload, mapping file, offline marks import, OCR correction, unmatched queue).
- `exam_integrity.dart` (+ `_web` / `_stub` conditional imports): integrity signals the platform can observe (tab switch, full-screen exit, copy / paste, app backgrounded), event kinds only, never content.
- `offline/`: offline sittings — the exam package is the server's AES-GCM ciphertext, the key is released only inside the exam window or passed from a nearby phone over the attendance relay link (`offline_exam_relay.dart`: every message X25519 + AES-GCM encrypted, the key only as per-student wraps), answers are sealed bundles and only the server's HMAC receipt counts as submitted. `offline_exam_core.dart` is the pure part; `offline_exam_service.dart` is the phone's encrypted store and sync; `_screen` (student) and `_teacher` (hand out / collect / bulk upload / auto-grade) are the UIs. Students sit offline on phones only. Server contract: `../back/exam_engine/services/offline.py`.
- `PasscodeSheet` (`lib/features/shared/passcode/passcode_screen.dart`) is the reusable PIN sheet (exam passcodes, private courses); the caller supplies `verify`.

**App assistant and the features guide** — `AppAssistantHost` (`lib/features/shared/rag/app_assistant.dart`, in `MaterialApp.builder`) floats the app assistant (`RagChatView(app: true)`) above every signed-in screen (kill switch `rag.app_assistant`; full-screen pages call `AppAssistant.hide()` / `release()`). It answers from the app library: uploaded guides plus the core's terms, about and **features guide** pages — and, while the person is in Organization mode, from that organization's library and synced rules too (`app: true` + `org_id`, `appAssistantOrg`, D-012). Answers come from the server's model pipeline (plan → search → write → verify, `../back/rag_service/pipeline.py`, D-054; by default a LOCAL open-weight model on the server, Qwen3 INT4 on ONNX Runtime, D-055 — answers take ≈ 10–15 s with the default 0.6B build and about a minute with the 1.7B, so the stage trail matters): `RagAnswer` carries `followUps`, `stage` and `generator`; `answerBlocks` renders paragraphs / bullets / numbered steps / **bold**; `RagStageTrail` shows the step while polling. An empty chat shows the server's starter questions (`RagApi.starters` → `GET /api/v1/rag/starters`, built from the headings the asker may read; `ragStartersFrom`), and the built-in `ragStarterPrompts` only when the library has none. The Super Admin's console is `rag_admin_console.dart` (`/api/v1/rag/admin/…`: settings, overview, playground with the trace, questions), opened from the admin services hub; `RagAdminSettings.llmLocal` / `light` (the local model's light profile) hide the effort / model knobs and the external-consent switch and show the model's files status instead. Exam drafts (`exam_generate.dart`) take `difficulty`, `focus`, `lang` and return `review` (what the planner / writer / reviewer agents did; `examGenSummary`). Tests: `test/org/rag_premium_test.dart`. **When you add a user-facing feature, add it to `../back/data/app_features_guide.json`** (group, roles, Arabic + English name, summary, place, steps, the kill-switch keys that hide it — D-052). The super admin manages the guide in `AdminFeatureGuidePage` (`lib/features/admin/admin_feature_guide.dart`, opened from the app assistant dashboard and the Features page): edit / add / delete, and per feature "App" (switches all its kill-switch keys on every platform) and "Assistant" (whether it is explained; a feature hidden in the app never is). **A new kill-switch key** goes into `../back/services/feature_catalog.py`, then regenerate the snapshots (same command as the API contract test): `test/contract/feature_keys_test.dart` fails on a key the catalog lacks, because a super admin could never switch it off.

**Server-driven theme & feature flags** — `ThemeConfigProvider` (`lib/config/theme/`) loads the theme from `GET /api/v1/theme/{platform}` and builds `materialTheme()`. Always read colors via `context.colors`, never hard-coded colors. The same response sets `AppConfig.disableList` (feature kill-switch ids, e.g. `profile.logout`, `teacher_tab_analysis`). To make UI switchable, wrap it in `ParentComponent(featureKey: '...')` (hides it), or give a `BasePage` a `ValueKey('<id>')` (shows a "coming soon" page). `AppConfig.setDisableList` rebuilds the whole widget tree when the list changes.

The disable list has layers. The effective list combines:
- the platform list from the theme response;
- the open organization's list (`AppConfig.setOrgDisableList`);
- `AppConfig.orgEntryKeys`, while the super admin has organizations switched off (`AppConfig.orgsEnabled` / `setOrgsEnabled`, from `orgs_enabled` in the theme response).

A super-admin OFF always wins, because an organization can only add keys. Hidden features disappear rather than greying out. With organizations off, the server answers 403 `orgs_disabled` on org routes, and `/org_dashboard` is wrapped in `OrgsGate`. The theme response's `platform_settings` also sets the platform timezone and 12h/24h (`AppTime.configurePlatform`).

**UI kit** — New screens should use `lib/design/app_kit.dart` (role-neutral aliases over the Data Lab / org / admin widgets: `AppHero`, `AppCard`, `AppStatTile`, `AppEmpty`, `AppListSkeleton` rather than spinners, `AppBanner`, `AppField`, `showAppSheet`, `appConfirm`, …; the header comment of that file has the full usage table) and wrap pages in `BasePage` (`lib/utils/widget/base_page.dart`), which handles the background, kill-switch, and the global upload-progress footer. App-wide rules the kit enforces:
- **Switches:** only `AppSwitch` / `AppSwitchTile` (`app_switch.dart`), never `Switch`/`SwitchListTile`.
- **Dropdowns:** only `AppDropdown`.
- **Displayed times and dates:** always go through `AppTime` (`lib/core/app_time.dart`, re-exported by the kit), which applies the platform or organization timezone and the 12h/24h choice. `AppTime.configureOrg` is set when an organization is opened and cleared when it is left.
- **Table exports:** use `showAppExportSheet(context, AppTableExport)` (`app_table_export.dart`, writers in `lib/design/export/`). It offers Excel, Word and PDF with a column picker, RTL and Arabic fonts, and remembers the last choice per table. Admin `PagedList`s take an `export:` option that fetches every page before exporting.
- **Keyboard (web / desktop):** `AppKeyboardSupport` in `MaterialApp.builder` (`lib/design/app_keyboard.dart`, D-012) handles every text field: Enter moves to the next field of the form and, on the last one, presses the form's primary button (`PrimaryButton` / `AppPrimaryButton` / `FilledButton` / `ElevatedButton`, the one nearest the field; a dialog with text buttons only presses the last one); Ctrl+Enter submits a multi-line field; a field with its own `onSubmitted` and a search / filter box are left alone; Esc leaves a field; Ctrl+K or "/" focuses the search box. Nothing to wire on a new screen; `EnterSubmits(onSubmit:)` / `EnterSubmits.none` decide by hand where the guess would be wrong (an exam's answer box). Tests: `test/ui/app_keyboard_test.dart`.

**Localization** — Strings live in `assets/translation.json` as `{ "key": { "en": "...", "ar": "..." } }`. Use `translate('key')` or `'key'.tr`; a missing key falls back to the key itself. Add both `en` and `ar` for every new key. Current language is `AppConfig.lang` (switched by `LangProvider`); use `pageDirection` for RTL/LTR.

**Offline** — `lib/core/offline/` holds connectivity (one app-wide online/offline answer, wired into `topRouteObserver`) and encrypted offline video downloads (AES-CTR via pointycastle). Offline attendance can relay through a nearby online classmate (`features/shared/attendance/`: `nearby_connections` between Android phones, plus a Bluetooth LE GATT transport in `relay_ble_transport.dart` for iPhones and Android ↔ iPhone — that file was written without checking the package source; see its header).

**Course video player (`lib/features/shared/session/video/`)** — `VideoPlayerScreen(material, playlist:)` is the one player for every caller (session material grid, course profile, downloads); it calls `POST …/materials/{id}/play` itself, plays the encrypted offline copy when `OfflineVideoService.localVariant` has one, and keeps screen protection (`screen_protector`) and wakelock on for the whole visit — switching lectures happens in place (`_openLecture`), never by pushing a second screen. Pure parts (resume logic `VodResume`, `vodPlaylist`/`vodNextOf`, next-up card, lecture list, HUD, captions, skeleton) live in `vod_player_parts.dart` so `test/ui/vod_player_layout_test.dart` can test them without a platform player; the full screen is tested only in its error state with `debugDefaultTargetPlatformOverride = TargetPlatform.iOS` (the Android PiP plugin leaks a timer in tests). Captions are server `.vtt` files (`captions_url`, uploaded by teachers via `POST …/materials/{id}/captions`) and are saved next to offline downloads. On phones swipes change the real screen brightness and media volume (`screen_brightness`, `volume_controller`); elsewhere the player dims/attenuates itself.

**Live room (`lib/features/teacher/sessions/live/`)** — `PreJoinPage(JoinArgs)` → `RoomPage`. The control bar is `widgets/live_control_bar.dart` (presentational, tested) driven by `widgets/controls.dart`; reactions are LiveKit data messages on topic `reaction` (`widgets/live_reactions.dart`). Recording: `sessions.record_enabled` is the creator's switch; `/live-sessions/start` and `/join` return `recording_enabled`, carried as `LiveResponseModel.recordingEnabled` → `RoomPage.recordingEnabled`; when false the teacher's device never starts the client recorder. Guest links: teacher `…/guest-link` routes + public `/api/v1/public/live/{token}` (`lib/features/shared/guest/guest_live_api.dart`, sheet in `teacher/sessions/components/guest_link_sheet.dart`, page `guest_live_page.dart` at route `/live/<token>`, feature key `live.guest_link`). `RoomPage(isGuest: true)` must never call an authenticated API (a 401 redirects to login); `canPublish: false` gives a listen-only bar. Backend: `../back/routers/live_guest_router.py`, `services/live_guest_service.py`, tests `tests/org_v2/e2e_live_guest_link.py`, `e2e_session_record_flag.py`.

**Live rooms: share link · lobby · meeting recordings (`lib/features/shared/live/`, spec `docs/backend/live-rooms-spec.md`, D-058)** — A live room is a course session or a calendar meeting (`LiveRoomRef(kind, id)` in `live_room.dart`; `JoinArgs.roomRef`, `isHost`). Every join (`…/join`, the public `/public/live/{token}/join`, the signed-in `POST /live/links/{token}/join`) may answer 202 `status: waiting` — `JoinOutcome.parse` tells it apart, `PreJoinPage` then shows `WaitingForHostPage` and polls `/live/requests/{id}` (or the public poll with the secret) until admitted. The host's `LiveLobbyController` (`live_lobby_sheets.dart`) polls `GET /live/{kind}/{id}/lobby` every 15 s in the room (4 s while `LobbySheet` is open, nothing in the background; intervals are constructor parameters), at once on the silent push `live_join_request` (plus one follow-up 4 s later) and on resume; `LobbySheet` admits / rejects and holds the two switches (`admission` open / approve for members, `guest_admission` approve / auto), `ShareLinkSheet` is the meeting's guest link, the notification deep link is `live_lobby`. Meetings (never course sessions) record to the creator's Google Drive / OneDrive: `meeting_recording.dart` + `meeting_recording_sheets.dart` (`RecordSetupSheet` destination + quality before the recorder starts, chunks to `POST /live/recordings/{rid}/chunk`, `RecordingStatusCard` in the meeting detail, `CloudDrivesPage` in settings, `GET /me/cloud` + OAuth in the browser). The participant tile is `ParticipantTileLayout` / `LiveAvatar` / `RecordingPlaceholderFrame` (`widgets/participant.dart`, `live_avatar.dart`, `recording_placeholder.dart`, plain values; the photo comes from the LiveKit token's `metadata.image_url`). Feature keys `live.lobby`, `live.share_link`, `live.meeting_recording`, `profile.cloud_drives`. Backend: `../back/routers/live_room_router.py`, `live_recording_router.py`, `services/live_room_service.py`, `live_recording_service.py`, `cloud_drive_service.py`, migration `0017_live_rooms`; tests `tests/org_v2/e2e_live_lobby.py`, `e2e_meeting_recording.py`; app tests `test/org/live_room_test.dart`, `test/org/meeting_recording_test.dart`, `test/ui/live_*_layout_test.dart`, `test/ui/meeting_recording_layout_test.dart`.

**Native code** — Live sessions use LiveKit (`features/teacher/sessions/live/`). Screen recording and screen sharing use platform channels (`com.example.flutter_education_app/native_recorder`, `/radios`). The native side is `android/app/src/main/kotlin/.../ScreenCaptureService.kt` and `MainActivity.kt`, and on iOS `ios/Runner/AppDelegate.swift`, `LocalDebugRecorder.swift`, and the `ios/BroadcastUploadExtension` target. Recordings upload in chunks.

**Organizations (`lib/features/org/`)** — The backend source is next door at `../back` (`routers/organization/`, `services/organization/`). Check payloads there; don't trust the notes alone. Shared logic lives in `org_v3.dart`: `orgCall` keeps `detail.code` and its extras, `orgErrorText` turns codes into bilingual text, and `JoinPolicyDraft` / `ScheduleDraft` build PUT bodies. Every finding carries `actions[]` — the ranked ways out (`ActionOption`: rank, score 0–100, `auto` = the server applies it, else "by hand"; a manual way is always listed; `best` = the first automatic one). `RankedActions` renders them; Accept posts `…/preflight/accept {key, action_id}` and "Accept every recommended fix" posts `…/preflight/accept-all`. Backend: `../back/services/organization/schedule_autopilot.py` (D-053);

  Generation has a hard 90 s budget: each round's solver only gets the time left, a run no worker started is failed after 2 minutes, and the app stops following after 5 errors or 4 minutes. `completion_pct` is never shown as complete while a session is unplaced, a hard clash remains or a proposal is pending. `QuickActionsPanel` (here, plugged into the studio through `studioQuickActions` in `org_schedule_pages.dart`) uses `GET/POST …/quick-actions[/apply]` (`../back/services/organization/schedule_quick.py`): each action relaxes one locked soft rule with a dry-run impact preview and re-solves only the affected sessions; hard rules answer 422 `rule_locked`;

- `org_schedule_optimizer.dart`: suggestion models and API (shown as last-resort advice in the generation result) and the days/periods horizon;
- `org_schedule_versions.dart`: pure ranking / diff / member-copy logic used by the copies page;
- `org_schedule_copies.dart`: full copies (revisions) and per-member copies, with export;
- `org_schedule_export.dart`: Excel and Word written by hand (SpreadsheetML / WordprocessingML zipped with `archive`) and PDF via `package:pdf` with the bundled Tajawal / Bahij fonts — per teacher / assistant / room / group or one member, merged cells for multi-period sessions, summaries.

Pure logic in those files (`planCourse`, `ScheduleHealth`, `ScheduleHorizon`, `compareVersions`, `diffVersions`, `memberTimetable`, `TimetableGrid`, `TimetableSummary`, `GridFilter`, `GenerationOutcome`, `rulesFlexible`, `PreflightReport`, `RemedyReport`, `ReassignPlan`, `OccurrenceChange`, `orgTodaySessions`) is what gets unit-tested, because `ApiClient` is a singleton and can't be faked.

When a backend route may be missing, call it through an `XxxApi` interface with a `Remote…` and a `Mock…` implementation. The mock is used only with `--dart-define=ORG_SCHEDULING_MOCKS=true` (`kOrgSchedulingMocks`, which is always false in release builds). A missing route is detected with `orgEndpointMissing` (FastAPI's bare 404 "Not Found" or a 405), and the UI then says the feature needs a server update. `docs/backend/scheduling-spec.md` specifies the scheduling backend work (G1–G5 are done in v3.4; G6 is optional). The backend may be changed when the task needs it. Follow `../back/CLAUDE.md`, add tests under `tests/org_v2/`, and record every org API contract change in `../back/FLUTTER_API_CHANGES.md`. The backend tests are standalone e2e scripts. Run them with Python 3.12 and `PYTHONUTF8=1`, for example `PYTHONUTF8=1 ../back/.venv312/Scripts/python ../back/tests/org_v2/e2e_org_v2.py` (or `py -3.12`). The `.venv312` folder is local and git-ignored; plain `python` is not on PATH. Schema changes are Alembic revisions (`../back/migrations/versions/`, idempotent helpers in `migrations/helpers.py`; the old `ensure_*_tables` are frozen as revision 0001 and do not run in production): a new column or table needs the model change AND a new revision, and the e2e scripts still build their schema from the models (`create_all` + `ensure_org_tables`), so put it in both. The e2e scripts need a database: without a local Postgres, give each run its own `DATABASE_URL="sqlite:///C:/…/x.db"`. Run them on PostgreSQL once before a deploy. Scheduling tests to know: `tests/org_v2/section_count_unit.py` (pre-flight, pure), `e2e_preflight_actions.py`, `e2e_remedies_reassign.py`, `e2e_quick_actions.py`, `e2e_schedule_auto.py`, `e2e_course_plans.py`; the generator needs `ortools` installed.

Registrar (credit-hour and traditional/year systems — registration, waitlists, grades, GPA, attendance denial, degree audit, decisions):
- **App:** `org_registrar.dart` holds pure helpers and code → text maps (`registrarCodeText`, `blockText`, decision kind/risk/action texts, `RegCart`); `org_registrar_member.dart` has the member screens (registration cart, record, teaching/grades, advising, staff consents, my week); `org_registrar_staff.dart` is `OrgRegistrarPage`, the Academics → "registrar" sub-page. A new server code or decision kind needs a label in `org_registrar.dart`.
- **Backend:** `routers/organization/org_registrar_router.py` (staff `/orgs/{id}/registrar`, members `/public/{id}/registrar`) over `services/organization/registrar/`: `policy.py` is pure (rule defaults, GPA, standing, calendar generation, `ruleset(system_type)`), `service.py` does eligibility/registration/grades/audit, `jobs.py` is the hourly tick (`_registrar_tick` in `scheduler_service.py`), plus `allocation.py`, `consent.py`, `traditional.py`. Tables are in `data/registrar_models.py`; new columns on existing tables go in `REGISTRAR_COLUMNS` (no Alembic, `ensure_registrar_tables` adds them).
- **Principles:** every rule is data (`org.settings` rules, inherited from parent orgs, editable in the Rules tab); ambiguous cases never hard-reject but open an `OrgDecision` (with risk, recommendation, alternatives) applied through the `ACTIONS` registry; seats are taken with a conditional UPDATE and waitlist promotion claims rows compare-and-set. Publishing a timetable that puts staff in their unavailable time waits for their consent (409 `staff_consent_pending`) unless an approver forces it with a reason.
- **Tests:** `tests/org_v2/e2e_registrar.py`, `e2e_traditional.py`, `registrar_race.py` (real threads; `RACE_DB_URL=postgresql://…` on an empty database to test Postgres), and `test/org/org_registrar_test.dart`.
