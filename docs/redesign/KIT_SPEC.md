# Phase 1: the kit (spec for the implementer)

Read with `START.md`, `BRANDS.md`, `DESIGN_SYSTEM.md`, `PHASE_PLAN.md` §3 and the root `CLAUDE.md`. Where this file and `PHASE_PLAN.md` §3 differ, this file wins (it was written after reading the code). Every existing rule still applies: tokens, `context.colors`, `appText`, no `dart format` on existing files, `expectNoLayoutErrors`, both languages.

Words used here: **role** = a named colour slot (never a hue name in widget code); **area** = one of the 11 student areas; **role accent** = the single accent of teacher / parent / admin / super admin; **reference** = the design in `D:/platform/redesign-ref/`.

Hard rules for this phase:

- No hex value and no product name in any widget. Hex lives in exactly two data files: `lib/config/theme/kit_palette_defaults.dart` and `lib/config/theme/app_theme.dart` (front), and `features/platform/theme_kit_defaults.py` and `features/platform/theme_presets.py` (back). The downstream product swaps those files in its own identity step; nothing else may carry a brand.
- No colour value of the reference's own brand is written in this repository, not in code, JSON or docs (D-1810). They are listed in the downstream repository (`docs/redesign/KIT_PALETTE_DOWNSTREAM.md` there). To compare, run `tool/redesign/kit_palette.py --ref <a JSON outside this repo>`. The shared functional colours (accents, subjects, status) are here by decision (BRANDS.md).
- No public constructor of the existing kit loses a parameter. New parameters are named and optional.

## 1. Palette

Generated by `tool/redesign/kit_palette.py` from the two logo seeds, green `#186848` and gold `#C08838`. `py -3.12 tool/redesign/kit_palette.py --check` must print `0 under the floor`; `--json` writes `tool/redesign/kit_palette.json`, which is the source the two defaults files are copied from. To change a colour, change the script, never the copies.

### 1.1 Decisions

| # | Decision | Why |
|---|---|---|
| P1 | Role names are `ink`, `deep`, `primary`, `partner`, `warm`, `hot` (reference: navy, deep, blue, cyan, apricot, coral). | A hue name would be wrong in one of the two products. |
| P2 | `primary` = the logo green as sampled. White on it is 6.75:1. `primary_ink` = `primary` (5.47:1 on its tint). | No shift needed. |
| P3 | `partner` `#2FA26C` is a gradient partner and the focus ring only. White on it is 3.23:1, so it never sits under text; a button's end stop is `btn_b` (darkened to 4.6:1). | AA. |
| P4 | The forward button (`hot`) is gold with the deep green text: `hot_a` → `hot_b`, text `hot_fg`. | White on the logo gold is 3.08:1. A gold dark enough for white (`hot` `#996C2D`) reads brown and stops being the brightest thing on the screen. BRANDS.md said "gold → deep gold"; this replaces it. |
| P5 | **Mint is moved** from hue 166 to 174 (`#19C2B1`) for this product. Its tint and ink are derived. | At 166 it sits 10° from the brand green and 14° from `partner`: "done" and the Quran area would read as the brand colour. |
| P6 | **Lime is not moved** (hue 81, 75° from the brand green). | No clash. |
| P7 | The other accents, the subjects and the status colours keep the design's own colour, tint and ink. All pass 4.5:1 on white and on their tint (table below). | Shared functional colours (BRANDS.md). |
| P8 | Subject `quran` `#1D9A63` (hue 154) is next to the brand green. It stays: it is a book-cover colour, never an action colour. | Same subject, same colour, in both products. |
| P9 | A hero's middle stop is the accent darkened until white reads at 6:1, then moved 30 % toward `ink` (12 % for sun, gold and deep gold, which turn olive with more green). End stop `deep`. | The reference mixes with navy and then hand-tunes; this is the same idea with the deep green, computed. |
| P10 | A filled button's text is white when both stops can be darkened to 4.6:1 without losing the hue (green, grape, pink, sky, mint, teal), and `deep` on the light yellows (sun, lime, gold). | The reference draws white on every button; several of those are under 3.5:1. |
| P11 | A count badge is `live_fill` `#CB474C` (white 4.62:1), not `live` (3.39:1). `live` is for dots, halos and gradients. | AA on 10–11 px digits. |
| P12 | Error text on a tint uses `error_ink`; `error` passes on white only. | 4.21:1 on its own tint. |
| P13 | The gold line on a hero (kicker, squiggle) is `warm_on_dark` `#E6D1B1`: 4.5:1 or more on the ink, the deep, the logo green and the admin hero's middle stop. The home, me and admin heroes start on the logo green (`#186848`), not the partner. The kicker is gold only where it reaches 4.5:1 on every hero stop (home, me, admin, teacher: `AppHero.kickerInk`, `GOLD_KICKER_HEROES` in `kit_palette.py`); elsewhere it is the on-hero ink. | The logo gold is 3.86:1 on `ink`; the earlier `#D0A66A` was 1.44:1 on the admin hero's `#2FA26C` corner. |
| P14 | Dark mode keeps the theme's neutral grey surfaces and text (D-650). A tint is the colour at 18 % over the dark card; an ink is the colour lightened until 4.6:1 on that tint. Heroes, buttons and solid accents do not change. | Smallest change that passes. |
| P15 | `danger`, `warning`, `purple` and `success` of the existing theme keep their current values. New kit widgets use `kit.status.*`. | Untouched screens must not change meaning. |

### 2.2 Existing roles stay

`context.colors.primary`, `accent2`, `success`, `onHero`, `heroShade`, the block tones, every gradient getter and every text style keep their meaning and their code. Only values move (2.3). Rules:

- A screen that was not redesigned reads the same getters as today and gets the new brand through them. Do not search-and-replace `c.primary` with `c.kit.primary`.
- New and restyled kit widgets read `c.kit.*` for the roles the old theme does not have (areas, accents, subjects, status, button stops, hero stops, `well`, `track`) and the old getters for the rest (`cardBg`, `background`, `textDark`, `textMedium`, `divider`, `onHero…`).
- `c.onHero`, `onHeroMuted`, `heroGlass`, `heroGlassBorder` are the ink and glass on every new hero, sidebar and top bar. No new "white" role.

```dart
// lib/design/motion/motion_budget.dart
enum MotionKind { flip, deal, wipe, wobble, pop, slap, ink, squiggle }

/// One per screen (AppAreaScope installs it). Entrance widgets ask it before they move.
class AppMotionBudget extends StatefulWidget {
  const AppMotionBudget({super.key, required this.child, this.maxEntries, this.maxLoops = 3,
      this.window = const Duration(milliseconds: 1200)});
  final int? maxEntries;          // null: 12 below Breakpoints.mobile, 24 from it
  static AppMotionBudgetState? maybeOf(BuildContext context);
}

class AppMotionBudgetState extends State<AppMotionBudget> {
  /// False = draw the end state at once. Refused when: (a) [kind] is a hero move (flip, deal, wipe, wobble) and a
  /// DIFFERENT hero move was already granted on this screen; (b) [maxEntries] grants were given; (c) [window] has
  /// passed since the scope was first built (an item scrolled into view later never animates).
  bool claimEntry(MotionKind kind);
  /// A loop asks once in initState; refused past [maxLoops]. A refused loop parks at rest for its lifetime.
  bool claimLoop(Object owner);
  void releaseLoop(Object owner);   // in dispose
}
```

- No budget above a widget (a dialog, the gallery, a test): every claim is granted.
- `pop`, `slap`, `ink`, `squiggle` are not hero moves but they count toward `maxEntries`.
- In debug builds a refusal for reason (a) prints one line per screen (`debugPrint`), naming both kinds; it never throws.
- M9, M10, M13, M14, M15 and `AppWipeSwitcher` do not ask the budget.
- Outside an area scope (`AppAreaScope.playful(context) == false`: teacher, parent, admin, super admin, organization) M1, M4–M8, M11, M12 and M16 draw their end state. M2 and M3 stay available to those roles for rings and the success tick only. This is enforced inside the widgets, so a role screen cannot opt in by mistake. The gallery passes `AppAreaScope(area: …)` to show them.
