## A-002 Certificate pinning is per identity

NextBrain's SPKI pin and legacy certificate pin are for nextbrain.site and must not ship in Alfaheem. The two pin
sets of `lib/core/cert_pin.dart` are written from `CERT_PIN_SPKI_SHA256` / `CERT_PIN_LEGACY_SHA256` in
`sync/identity.env`, both empty today. With empty sets a mobile build accepts the API host only through the backup
rule: a leaf for the API host, in date, signed by one of the bundled Let's Encrypt intermediates. Any other
certificate (another CA, a proxy, a user CA) is still refused, because the system roots are never consulted.

The iOS Google sign-in client (REVERSED_CLIENT_ID) is wired the same way.

Original TODO: once the alfheemacademy.com certificate exists (issued with `certbot ... --reuse-key`), read its SPKI

## A-005 Syncing with NextBrain

NextBrain flows into Alfaheem by real git merges from a fetch-only remote (`nextbrain`, push URL `DISABLED`); nothing
ever flows back. `sync/sync.sh` merges, keeps Alfaheem's files (`sync/keep_paths.txt`, `sync/brand_assets.txt`),
takes NextBrain's version of every other conflict, re-applies the identity and runs the gate. Alfaheem has no code of
its own: anything Alfaheem changes outside the two lists must be produced by `sync/apply_identity.py`, or the next
sync loses it.

## A-006 Firebase project alfaheem-d3c8f (2026-11-14)

Alfaheem runs on its own Firebase project `alfaheem-d3c8f` (number 887854198161, owner account alfaheem.2y@gmail.com),
apps registered for `com.doubley.alfaheem`: Android, iOS (the macOS app reuses the iOS app and plist, same bundle id)

  (`app-1-887854198161-ios-ffa59d7c85f3ac430afe30`; the Google sign-in `REVERSED_CLIENT_ID` scheme only once

  Project settings, Cloud Messaging, Web Push certificates). NextBrain's key must not ship. Should the value ever be

  unaffected.
