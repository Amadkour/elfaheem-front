# App versions through Codemagic (D-144, builds on D-143) — shared contract

The owner's change (2026-11-02): every version has ONE of two download channels, and Codemagic does ALL builds.
- `store`   → Codemagic builds AND uploads to the store (Google Play; App Store when configured). No files on our side.
- `website` → Codemagic builds, the build's last step uploads the files to OUR server, which stores them in MinIO;
  users download them from a banner at the top of the website and from the in-app update dialog.
The D-143 pull agent (`tools/builder/`) is no longer the build path. Keep its code and API (tests stay green) but the
release's executor is `codemagic`; D-144 records that it supersedes the build-server part of D-143.

## Platforms × channels
| platform | store | website |
|---|---|---|
| android | Google Play via Codemagic (AAB, track) | APKs (arm64-v8a, armeabi-v7a, universal) → MinIO |
| ios | App Store via Codemagic — OFF until configured (owner decides after the free-install research) | not possible (Apple): the PWA; the option shows the PWA note, plus the research result if it finds a practical free method |
| web | — | the website itself: Codemagic builds web, uploads a zip, the server unpacks it into APP_RELEASES_DIR/web/<id> and switches `current` (D-143 mechanics) |
| linux | — | .deb + .tar.gz (Codemagic linux machine) → MinIO |
| windows | Microsoft Store: record only (not in phase 1) | zip of the release folder (Codemagic windows machine) → MinIO |
| macos | record only | record only |

## Configuration (env in `.env.production`, defaults; non-secret ones editable per version)
Secrets (env ONLY, never in the form, never returned — the API returns only `set: true/false`):
- `CODEMAGIC_API_TOKEN` — Codemagic → Teams/User settings → Integrations → Codemagic API.
- `APP_RELEASE_UPLOAD_SECRET` — HMAC key for the per-release upload token (generated by the server if empty? NO: required for the website channel; check_env tells the admin).
Non-secret defaults (env; the New version form is prefilled from them and may override per version; overrides are
stored on the release row `config{}`):
- `CODEMAGIC_APP_ID` — the Codemagic application id of the front repo.
- `CODEMAGIC_WORKFLOW_ANDROID_STORE=android-store`, `CODEMAGIC_WORKFLOW_ANDROID_WEBSITE=android-website`,
  `CODEMAGIC_WORKFLOW_IOS_STORE=ios-store`, `CODEMAGIC_WORKFLOW_WEB=web-website`,
  `CODEMAGIC_WORKFLOW_LINUX=linux-website`, `CODEMAGIC_WORKFLOW_WINDOWS=windows-website` (= the ids in `codemagic.yaml`).
- `PLAY_PACKAGE_NAME` (must not start with `com.example.` — Google Play refuses it; today's applicationId is
  `com.example.flutter_education_app`, so the store option is NOT ready until the owner picks a real id),
  `PLAY_TRACK=internal` (internal|alpha|beta|production), `PLAY_STORE_URL` (default
  `https://play.google.com/store/apps/details?id=<PLAY_PACKAGE_NAME>`).
- `APP_STORE_APP_ID`, `IOS_BUNDLE_ID` (today `com.softkour.alfaheem`), `APP_STORE_URL`.
- `APP_RELEASES_BUCKET=app-releases` (MinIO, private; downloads are served through our API, see below).
- `NB_PUBLIC_API_URL` (default `https://nextbrain.site/api`) — passed to Codemagic so the upload step can reach us.
Signing material lives in Codemagic (Android keystore, Play service-account JSON, App Store Connect API key are set up by
the owner in Codemagic's UI / environment groups `play_store`, `app_store`, `android_signing`) — never in our repos or env.

## Readiness (drives the disabled Confirm button)
`GET /api/v1/admin/app-releases/config` → `{codemagic: {ready, missing:[...]}, channels: {"android:store": {ready,
missing:["PLAY_PACKAGE_NAME", ...], reasons_ar/en?}, "android:website": {...}, "ios:store": {...}, "web:website": ...},
defaults: {android: {workflow, track, package_name, store_url}, ios: {...}, ...}}`. `missing` holds env names (and the
code `package_name_example` when the package is com.example.*). The form disables Confirm for a (platform, channel)
that is not ready and lists what is missing, bilingual. `POST /` re-checks and answers 400 `channel_not_configured`
{missing:[…]} so a stale form cannot slip through.

## Release lifecycle (status values unchanged from D-143)
1. `POST /api/v1/admin/app-releases` gains `channel: store|website` (replaces `source`; keep accepting the old
   `source` values: website→website, google_play/app_store→store, custom→website with store_url) and `config: {workflow?,
   track?, package_name?, store_url?, branch}` overrides. Password re-auth as before. Branch default `production`.
2. The server starts the build at once (no queue on our side, Codemagic queues): `POST https://api.codemagic.io/builds`
   (header `x-auth-token`), body `{appId, workflowId, branch, environment: {variables: {NB_RELEASE_ID, NB_BUILD_NAME,
   NB_BUILD_NUMBER, NB_NOTES_EN, NB_NOTES_AR, NB_PLAY_TRACK, NB_PACKAGE_NAME, NB_GATE (test_first|direct), NB_API_URL,
   NB_UPLOAD_TOKEN (website channel only)}}, labels: ["nb-release-<id>"]}` → stores `codemagic_build_id`. A Codemagic
   failure → status `failed` with its message. Verify the exact API shapes against docs.codemagic.io (REST API: builds).
3. Status sync: a worker tick (every 30 s while any release is building; use the existing worker scheduling) calls
   `GET https://api.codemagic.io/builds/{id}` and maps Codemagic statuses → ours (queued/preparing/fetching → queued,
   building/testing → building or testing, publishing/finishing → uploading, finished → ready/live, failed/timeout/
   skipped → failed, canceled → canceled), appends step changes to the release log, sends `app_release_updated`.
   Optional webhook `POST /api/v1/app-releases/codemagic/webhook` (secret in the URL query, constant-time compare) only
   speeds it up; the poll is the truth. Cancel → `POST https://api.codemagic.io/builds/{id}/cancel`. Retry → a new
   Codemagic build for the same release (attempt + 1, new upload token).
4. Store channel finished → `live` when auto_publish (the store upload already happened inside Codemagic; for
   Play `production` / App Store it means "submitted", the store's review still applies — say so in the UI).
   The AppVersion row is written as in D-143 (policy → min_supported), the update dialog opens the store URL.
5. Website channel: the Codemagic workflow's last step uploads each file:
   `PUT /api/v1/app-releases/upload/{release_id}/{name}` with `Authorization: Upload <NB_UPLOAD_TOKEN>` (HMAC of
   release id + attempt with APP_RELEASE_UPLOAD_SECRET, expires 6 h), body = the file, header `X-Sha256`; size cap
   APP_RELEASE_MAX_UPLOAD_MB; names `^[A-Za-z0-9._-]{1,120}$`. The server streams it into MinIO
   `app-releases/<platform>/<version>+<build>/<name>`, verifies sha256, records the artifact. Then
   `POST /api/v1/app-releases/upload/{release_id}/done`. When the Codemagic build is `finished` AND done was called →
   `ready` → `live` when auto_publish (web: unpack + switch; others: become the platform's current download).
6. Downloads (public, no auth, rate-limited like other public routes):
   `GET /api/v1/app/downloads` → `[{platform, version, build_number, notes_ar, notes_en, files:[{name, size, sha256,
   abi?, kind: apk|deb|tar|zip, url}]}]` for every platform whose CURRENT release is on the website channel;
   `GET /api/v1/app/downloads/{platform}/{name}` → streams the MinIO object (Content-Disposition attachment,
   Range support), or 302 to a presigned URL if the existing MinIO helper already has a public-URL pattern
   (services/minio_service.py — reuse it, don't invent a second one).
   `GET /app/version-check` keeps D-143's `download_url` / `source` / `notes`: website → the best file for the
   platform (android: the universal APK), store → the store URL.
7. Rollback (website channel, web too): the previous live release of that platform becomes current again (its MinIO
   objects are kept: the newest 3 live releases per platform keep their files, older ones are deleted by the tick).

## Front repo
- `codemagic.yaml` at the repo root with the six workflows above. Each reads the NB_* variables; `--build-name` /
  `--build-number`; `NB_GATE=test_first` runs `flutter analyze --no-fatal-infos --fatal-warnings` + the CI test suites
  before building. android-store: `flutter build appbundle --release` (obfuscated like scripts/build_release.sh),
  signing via `android_signing` keystore reference, publishing `google_play` (credentials from the `play_store` group,
  track from NB_PLAY_TRACK). android-website: `flutter build apk --release --split-per-abi` + a universal APK, then the
  upload script. web-website: `flutter build web --release --dart-define=API_BASE_URL=https://nextbrain.site/api
  --dart-define=LIVEKIT_URL=wss://nextbrain.site/livekit`, zip, upload. linux: scripts/release/build_linux.sh packaging.
  windows: `flutter build windows --release`, zip. ios-store: ios_signing + app_store_connect publishing (only used
  when configured). The upload script: `scripts/release/upload_artifacts.sh <dir>` (curl PUT each file + done).
  Note the package-name issue in a comment; NB_PACKAGE_NAME is not applied to the build in phase 1 (changing the
  applicationId is the owner's decision: it makes a different app and needs a new google-services.json client).
- New version form: channel picker (Store / My website) per platform with only the valid channels; the config
  fields prefilled from `defaults` and editable (workflow, track, package name, store URL; never secrets); a
  readiness box listing what is missing; Confirm disabled while not ready.
- Website download banner (web only): a slim strip at the top of the web app (also on the login page), from
  `GET /app/downloads`: shows the visitor's platform first (Android phone → the APK; Windows / Linux desktop →
  that file; iPhone → "Add to Home Screen" PWA steps), "Other downloads" lists all; dismissible, remembered per
  browser for this version (a new version shows it again). Kill switch `app.download_banner`.
- The release page shows the Codemagic build link (`https://codemagic.io/app/<appId>/build/<buildId>`) and the store
  review note for store releases.
