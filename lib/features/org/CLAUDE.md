# Organizations — `lib/features/org/`

This file is loaded when working in this folder; the app-wide rules are in the root `CLAUDE.md`.

**Organizations (`lib/features/org/`)** — The backend source is next door at `../back` (`routers/organization/`, `services/organization/`). Check payloads there; don't trust the notes alone. Shared logic lives in `org_v3.dart`: `orgCall` keeps `detail.code` and its extras, `orgErrorText` turns codes into bilingual text, and `JoinPolicyDraft` / `ScheduleDraft` build PUT bodies. Several org PUTs replace the whole object (join policy, schedule, room, program, academic settings), so always send every field. The server stores naive UTC: send `orgUtc()` and read `orgParseUtc()`. Org screens use `t(ar, en)` from `admin_common.dart` for inline strings instead of `translation.json`. When you add a server error code, map it in `orgErrorText`. Tests: `flutter test test/org/`.

Entry points by role:
- **Every non-student org role** (org admin, sub-admin, staff, member without rights) opens ONE dashboard, `org_dashboard_screen.dart` (D-103, spec `docs/backend/org-dashboard-spec.md`): sections, with counts from one `GET …/dashboard` call; the organizations come from `GET /org/mine?members=1` (`access` admin · staff · member, `orgAccessOf`), held by `OrgSession` (`org_providers.dart`). The home's parts are in `lib/features/org/home/` (pure logic in `org_home_logic.dart`). Every page carries `OrgPageHeader` (`org_page_header.dart`: title · one primary action · Refresh · calendar · bell · the context switcher), so the shell's own top bar is off there. Students get a 403 `student_forbidden` on the dashboard / search APIs and see a "This dashboard is for staff" page; `org_access_changed` or a 403 `org_forbidden` / `student_forbidden` reloads the organization list. A department or academic program opens `org_department_dashboard.dart`.
- **Students** get `org_member_dashboard.dart` (`/org_member`), which serves students of several organizations, and the unified inbox (`lib/features/messaging/inbox/unified_inbox.dart`, `GET /me/inbox`).
- **Mode:** `AppModeController.instance` (`lib/core/app_mode.dart`) holds the Organization/Individual mode and the selected organization. Notification taps that carry `org_id` call `openOrg(id)` before routing. To go back to the personal account use `leaveToPersonal` / `ContextExitButton` (`lib/design/context_switcher.dart`): it clears the org timezone and disable list and pops every org page. Switching the mode alone leaves the org page open. Every org screen needs a way out: the dashboard's pages get it from the switcher's "Personal" entry in `OrgPageHeader`, and other org screens use `ContextExitButton`.

Other org areas:
- **Joining:** codes and requests, `org_access_joining.dart`, QR scan via `mobile_scanner` in `org_join_scan.dart`, mobile only.
- **Academic levels and prerequisites:** pure logic in `org_levels.dart`, screens in `org_levels_pages.dart`.
- **Announcements with engagement analytics:** `org_announcements.dart`, which includes the embeddable `OrgAnnouncementFeed`.
- **Platform and organization settings:** `admin_platform_*` and `org_platform_settings_page.dart`; the creation fee is in `org_creation_fee.dart`.
- **Join methods:** a unit can offer several at once (automatic, request, code/QR/link, code + request); `JoinPolicyDraft` in `org_v3.dart` keeps the legacy `method` field in sync for older clients.
- **Complaints reports:** `org_reports/` (period → layout designer or uploaded Word/Excel template → PDF/Word/Excel, signature background removal, share in-app or by e-mail; recipients use `OrgReceivedReportsPage`). Backend: `routers/organization/org_reports_router.py`.

**Governance: requests · complaints · forms · routing · delegation · councils · Export Hub (`lib/features/org/governance/`, D-057)** — Contract: `docs/backend/governance-spec.md`; backend `../back/services/organization/governance/`. Entities are departments with a `kind` (service · scientific · council · office · custom); a scientific department owns its Department Council (its team = the council members), the Faculty Council is a council entity without a parent. `gov_models.dart` (pure: `WorkItem`, `WorkRoute`, `Delegation.covers`, `Council`, `CouncilSession`, `AgendaItem`, `VoteTally.compute` = the server's tally rules, label maps, `govCodeTexts` merged into `orgErrorText`), `gov_api.dart` (`GovApi(orgId)`, one method per route; static `GovApi.member*` for the member side), `gov_filter.dart` (THE shared filter: `ItemFilter` ↔ query + `ItemFilterBar`, saved per user on the server — every item list builds on it), `gov_items_page.dart` / `gov_item_screen.dart` / `gov_route_sheet.dart` (list · item · route / escalate / decide with `version` → 409 `already_decided`), `gov_entities_page.dart`, `gov_delegations_page.dart` (scoped by default, global by its own button, dated, revocable), `gov_forms_assign.dart`, `gov_councils_page.dart` / `gov_council_settings.dart` / `gov_session_screen.dart` / `gov_my_votes.dart`, `gov_member_pages.dart` (submit · my items · my assignments; a department's team member may send a request straight to its Department Council with `to_council`), `gov_settings_page.dart` (org admin: routing rules · SLA hours · e-mail channel). The person who submitted an item never votes on it (`own_item`; `AgendaItem.excluded`, left out of `eligible_count`, of `/me/votes` and of the badge). An item sent to a council by mistake is pulled back with Recall (`POST …/recall`, only before voting). Requests for someone else (D-140): `GovForSection` on the submit form and the staff New item sheet ("For: Me / A member / Someone outside the system", shown where the entity's `can_submit_for_others`), `BeneficiaryDraft.validate` mirrors the server's rules, the member picker is `GET …/public/governance/{org}/people`; attachments are real uploads (`uploadGovAttachment` → `{id}`, opened with `openGovAttachment`: a fresh 10-minute link, images previewed in the app); export one / the selected items with `govExportItemIds` (`ids=`). Approval chain (D-141): `GovChainCard` on the item page, `GovChainPreview` on the submit form, `GovChainEditorPage` as the entity page's tab (org admin edits); a rejection needs a reason; the requester resubmits a rejected item (`showGovResubmitSheet`). After approval (D-890 – D-893): `gov_forward_sheet.dart` forwards an APPROVED item (`can.forward`) to the faculty council, an outside party or a person with required actions + deadline (`forwardBody` / `forwardProblem`); the recipient answers each action once (`GovForwardTaskCard`, member route `GovApi.memberAnswerRoute`); a department's New item sheet records an outside request (`external_source`, routed to its council by the server, setting `external_routing`); council settings carry `majority_pct` and `VoteTally` never decides without a vote. Tests `test/org/gov_workflow_test.dart`, `test/ui/gov_workflow_layout_test.dart`. Pure parts and widgets: `gov_request_parts.dart`; tests `test/org/gov_requests_test.dart`, `test/ui/gov_requests_layout_test.dart`. Services section entries `governance` · `entities` · `councils` · `votes` (attention keys `work_pending` · `council_votes` on `org.services`), `gov_wiring.dart` holds every plug-in point (dashboard subs, member pills, deep links, export callbacks); deep links `org_work` (item) and `org_council` (session) in `AppNavigator`; kill switch `org.governance` (+ `org.governance.export_hub`). The Export Hub (`lib/design/export_hub/`) generalises the complaints report designer: `export_design.dart` (pure design document: page, fonts per element, many logos / signatures, table style, the council items block with the vote result beside / below), writers `export_pdf.dart` / `export_docx.dart` / `export_xlsx.dart`, `export_designer.dart` (drag-and-drop with live preview), `export_hub.dart` (`exportHub(context, dataset)`: format · language ar / en / both with SEPARATE templates · template picker · content switches by permission · column picker); `AppTableExport` offers "Design…" into it. Tests: `test/org/gov_*_test.dart`, `test/ui/gov_*_layout_test.dart`, `test/export/export_hub_test.dart`.

**Academic Advising (`lib/features/org/advising/`, D-289)** — advisors, the workspace and student 360, appointments and conversations, early warning, requests and support plans, analytics and group outreach, the student hub. Files prefixed `adv_`; each phase's models / API client / texts / pages, a page that loads over a plain-value view. Staff routes `/orgs/{org}/advising/…`, the student's own `/public/{org}/advising/…`; what the caller may do comes from `GET …/advising/status` `me`. Kill switches `org.advising` (+ `.warning`, `.analytics`, `.outreach`); every plug-in point and deep link is in `adv_wiring.dart`. Read `docs/guides/advising.md` (files, flows, kill switches, deep links, tests) before working here; plan and history in `docs/advising/`.

Timetables: `OrgScheduleProvider` (`org_providers.dart`) holds the open schedule, its slots, and the conflicts from `GET …/validate`. Its writes send `expected_version`, and a 409 `stale_version` reloads the timetable. The screens are split across these files:
- `org_schedule_hub.dart`: `TimetableJourney` + the next-step banner;
- `org_schedule_pages.dart`: the studio — one toolbar (Generate · Add session · Result & conflicts · Publish, the rest under ⋮), the grid with drag-and-drop (a hard rule blocks the move, a soft one warns), the add/edit form validated live with `dry_run`;
- `org_schedule_grid.dart`: the single filter bar (program/level, instructor, TA, room, group, student) and the grid index; `org_schedule_board.dart`: the wide periods × days board with sticky headers and the session-details dialog;
- `org_schedule_insights.dart`: pre-flight (`GET …/preflight`, `DataHealthCard`), the quality report after a generation, and "why here" for a placed session. Every finding carries `actions[]` — the ranked ways out (`ActionOption`: rank, score 0–100, `auto` = the server applies it, else "by hand"; a manual way is always listed; `best` = the first automatic one). `RankedActions` renders them; Accept posts `…/preflight/accept {key, action_id}` and "Accept every recommended fix" posts `…/preflight/accept-all`. An older server that only sends `action` is turned into one option;
- `org_schedule_remedies.dart`: `GET …/remedies` gives every validator conflict the same ranked `actions` shape (move to a free time, change room, give it to a free colleague, fix the group, unpin, re-solve, override with a reason, …); `RemediesPanel` replaces the plain conflicts list in the Quick Actions sheet; `POST …/remedies/apply` (409 `schedule_conflict` → retry with `force`, 422 `reason_required` for override). Backend: `../back/services/organization/schedule_remedies.py`, `schedule_preflight.py`;
- `org_schedule_reassign.dart`: changing who teaches a session from the slot sheet asks the scope (`askReassignScope`: whole course · this weekly session · one date), dry-runs `POST …/slots/{id}/reassign?dry_run=true` and shows `ReassignCompareSheet` — Before / After with metrics, rank and the moved sessions; apply writes both as revisions and answers 409 `reassign_not_better` unless `force`. Scope "once" writes a one-date occurrence instead. Pin / unpin is `PUT …/slots/{id} {locked}` (`setLocked`). Backend: `schedule_reassign.py`;
- `org_member_changes.dart`, `org_member_today.dart`: one-date changes (substitute · online / offline · cancelled) as `/public/schedule/me` reports them in `changes` and `/me/calendar` applies them; `OccurrenceCard` lets students Accept / Reject and the staff undo; a session's own teacher / assistant taps it on "Today" or in "My timetable" to hold a date online (`switchSessionMode`, students are notified). Backend: `schedule_occurrences.py`, tables `org_schedule_occurrences` / `…_responses`;
- `org_schedule_ical.dart`: the timetable as an `.ics` with weekly RRULEs, built in the app;
- `org_schedule_autopilot.dart` + `org_schedule_preview.dart`: the Power AI flow — `TermTimetableCard` ("Generate now" for the current / next term without a timetable: `POST …/schedules/auto {term_id}`, also the dashboard attention key `term_without_timetable` and the `org_timetable` notification deep link via `timetableRequest`), the autopilot (`POST …/schedules/{sid}/autopilot`: data fixes → complete generation → every validated automatic remedy → re-solve, ONE run the studio follows; `AutopilotReport` from `result.autopilot`), and the BEFORE / AFTER preview of every remedy and quick action on two `MiniTimetable` grids (`POST …/remedies/preview`, `ChangePlan`, `applyChanges`). Backend: `../back/services/organization/schedule_autopilot.py` (D-053);
- `org_schedule_ladder.dart` + `org_schedule_ladder_ui.dart`: the relaxation LADDER, what "Create timetable" and the wizard run now (D-013; backend `../back/services/organization/schedule_ladder.py`, D-056, spec `docs/backend/ladder-spec.md`). `POST …/generate {ladder: true, auto}` → strict solve, then the timetable's rungs in priority order (free_moves · ta_limits · doctor_limits · rooms · split_groups · open_times · student_times · capacity · student_clash, each `auto` / `ask` / `locked`, `GET/PUT …/ladder`, presets `…/ladder-presets`) until every session is placed (a rung that cannot touch what blocks the remaining sessions is set aside and retried only when nothing else completes; a split group goes to an eligible colleague; a proposed room is deleted again when its proposal is rejected); a fork pauses the run (`status: waiting`, `summary.decision`) until `POST …/runs/{rid}/decide`. Pure models (`LadderConfig`, `LadderDecision`, `LadderLive`, `LadderReport`) in the first file; `LadderEditor` (reorder, modes, options, presets), `LadderOverlay` / `LadderLivePanel` / `LadderVeil` (the live follow), `LadderDecisionCard` and `LadderResultCard` in the second, all taking plain values (`test/ui/ladder_layout_test.dart`). The result is proven by the server's independent validator (`result.ladder.proof`); what the ladder added (rooms, periods, days, group splits) is real after the save and every bent rule is a pending proposal. Tests: `test/org/org_schedule_ladder_test.dart`; backend `tests/org_v2/ladder_unit.py`, `ladder_stress.py`, `e2e_generate_ladder.py`;
- `org_schedule_generate.dart`: the older "Generate timetable" action (`complete: true` — strict, then only the rules the admin marks Flexible; kept as the fallback for an older server and for the quick actions' `settings.rules`), the live panel, and the result sheet where every broken rule is a proposal to accept or reject (publishing waits: 409 `proposals_pending`). The server also creates and generates a draft per open term by itself (`../back/services/organization/schedule_auto.py`, now a ladder run);
- `org_schedule_groups.dart`: students per lecture/lab group, alphabetical / by-ID distribution, moves re-checked for clashes and capacity, roster export;
- `org_schedule_exams.dart`, `org_my_exams.dart`: midterm/final exam timetables and the member's own exams. A published exam window pauses the term's weekly classes (`pause_weekly`). That pause is applied where the app computes today's and the next sessions, because no server route expands weekly slots into dates;
  Generation has a hard 90 s budget: each round's solver only gets the time left, a run no worker started is failed after 2 minutes, and the app stops following after 5 errors or 4 minutes. `completion_pct` is never shown as complete while a session is unplaced, a hard clash remains or a proposal is pending. `QuickActionsPanel` (here, plugged into the studio through `studioQuickActions` in `org_schedule_pages.dart`) uses `GET/POST …/quick-actions[/apply]` (`../back/services/organization/schedule_quick.py`): each action relaxes one locked soft rule with a dry-run impact preview and re-solves only the affected sessions; hard rules answer 422 `rule_locked`;
- `org_schedule_planning.dart`: enrollment estimates and lecture/lab groups;
- `org_schedule_optimizer.dart`: suggestion models and API (shown as last-resort advice in the generation result) and the days/periods horizon;
- `org_schedule_versions.dart`: pure ranking / diff / member-copy logic used by the copies page;
- `org_schedule_copies.dart`: full copies (revisions) and per-member copies, with export;
- `org_schedule_export.dart`: Excel and Word written by hand (SpreadsheetML / WordprocessingML zipped with `archive`) and PDF via `package:pdf` with the bundled Tajawal / Bahij fonts — per teacher / assistant / room / group or one member, merged cells for multi-period sessions, summaries.

Pure logic in those files (`planCourse`, `ScheduleHealth`, `ScheduleHorizon`, `compareVersions`, `diffVersions`, `memberTimetable`, `TimetableGrid`, `TimetableSummary`, `GridFilter`, `GenerationOutcome`, `rulesFlexible`, `PreflightReport`, `RemedyReport`, `ReassignPlan`, `OccurrenceChange`, `orgTodaySessions`) is what gets unit-tested: `ApiClient` is a singleton, and the only fake is `FakeApi` at the HTTP-adapter level (above), so screen logic that should be tested without a route table belongs in pure functions.

When a backend route may be missing, call it through an `XxxApi` interface with a `Remote…` and a `Mock…` implementation. The mock is used only with `--dart-define=ORG_SCHEDULING_MOCKS=true` (`kOrgSchedulingMocks`, which is always false in release builds). A missing route is detected with `orgEndpointMissing` (FastAPI's bare 404 "Not Found" or a 405), and the UI then says the feature needs a server update. `docs/backend/scheduling-spec.md` specifies the scheduling backend work (G1–G5 are done in v3.4; G6 is optional). The backend may be changed when the task needs it. Follow `../back/CLAUDE.md`, add tests under `tests/org_v2/`, and record every org API contract change in `../back/FLUTTER_API_CHANGES.md`. The backend tests are standalone e2e scripts. Run them with Python 3.12 and `PYTHONUTF8=1`, for example `PYTHONUTF8=1 ../back/.venv312/Scripts/python ../back/tests/org_v2/e2e_org_v2.py` (or `py -3.12`). The `.venv312` folder is local and git-ignored; plain `python` is not on PATH. Schema changes are Alembic revisions (`../back/migrations/versions/`, idempotent helpers in `migrations/helpers.py`; the old `ensure_*_tables` are frozen as revision 0001 and do not run in production): a new column or table needs the model change AND a new revision, and the e2e scripts still build their schema from the models (`create_all` + `ensure_org_tables`), so put it in both. The e2e scripts need a database: without a local Postgres, give each run its own `DATABASE_URL="sqlite:///C:/…/x.db"`. Run them on PostgreSQL once before a deploy. Scheduling tests to know: `tests/org_v2/section_count_unit.py` (pre-flight, pure), `e2e_preflight_actions.py`, `e2e_remedies_reassign.py`, `e2e_quick_actions.py`, `e2e_schedule_auto.py`, `e2e_course_plans.py`; the generator needs `ortools` installed.

Registrar (credit-hour and traditional/year systems — registration, waitlists, grades, GPA, attendance denial, degree audit, decisions):
- **App:** `org_registrar.dart` holds pure helpers and code → text maps (`registrarCodeText`, `blockText`, decision kind/risk/action texts, `RegCart`); `org_registrar_member.dart` has the member screens (registration cart, record, teaching/grades, advising, staff consents, my week); `org_registrar_staff.dart` is `OrgRegistrarPage`, the Academics → "registrar" sub-page. A new server code or decision kind needs a label in `org_registrar.dart`.
- **Backend:** `routers/organization/org_registrar_router.py` (staff `/orgs/{id}/registrar`, members `/public/{id}/registrar`) over `services/organization/registrar/`: `policy.py` is pure (rule defaults, GPA, standing, calendar generation, `ruleset(system_type)`), `service.py` does eligibility/registration/grades/audit, `jobs.py` is the hourly tick (`_registrar_tick` in `scheduler_service.py`), plus `allocation.py`, `consent.py`, `traditional.py`. Tables are in `data/registrar_models.py`; new columns on existing tables go in `REGISTRAR_COLUMNS` (no Alembic, `ensure_registrar_tables` adds them).
- **Principles:** every rule is data (`org.settings` rules, inherited from parent orgs, editable in the Rules tab); ambiguous cases never hard-reject but open an `OrgDecision` (with risk, recommendation, alternatives) applied through the `ACTIONS` registry; seats are taken with a conditional UPDATE and waitlist promotion claims rows compare-and-set. Publishing a timetable that puts staff in their unavailable time waits for their consent (409 `staff_consent_pending`) unless an approver forces it with a reason.
- **Tests:** `tests/org_v2/e2e_registrar.py`, `e2e_traditional.py`, `registrar_race.py` (real threads; `RACE_DB_URL=postgresql://…` on an empty database to test Postgres), and `test/org/org_registrar_test.dart`.
