# Live room — `lib/features/teacher/sessions/live/`

This file is loaded when working in this folder; the app-wide rules are in the root `CLAUDE.md`. Rooms, lobby, share links, meeting recordings and points: `lib/features/shared/live/CLAUDE.md`.

**Live room (`lib/features/teacher/sessions/live/`)** — `PreJoinPage(JoinArgs)` → `RoomPage`. The control bar is `widgets/live_control_bar.dart` (presentational, tested) driven by `widgets/controls.dart`; reactions are LiveKit data messages on topic `reaction` (`widgets/live_reactions.dart`). Recording: `sessions.record_enabled` is the creator's switch; `/live-sessions/start` and `/join` return `recording_enabled`, carried as `LiveResponseModel.recordingEnabled` → `RoomPage.recordingEnabled`; when false the teacher's device never starts the client recorder. Guest links: teacher `…/guest-link` routes + public `/api/v1/public/live/{token}` (`lib/features/shared/guest/guest_live_api.dart`, sheet in `teacher/sessions/components/guest_link_sheet.dart`, page `guest_live_page.dart` at route `/live/<token>`, feature key `live.guest_link`). `RoomPage(isGuest: true)` must never call an authenticated API (a 401 redirects to login); `canPublish: false` gives a listen-only bar. Backend: `../back/routers/live_guest_router.py`, `services/live_guest_service.py`, tests `tests/org_v2/e2e_live_guest_link.py`, `e2e_session_record_flag.py`.

**Live media, sharing and drawing (D-078 – D-098; working notes in `docs/live/`, `NOTES.md` first; open work: `docs/live/NEXT_SESSION.md` — start there)** — LiveKit stays the SFU (D-078). Every live start / join payload carries `live_config` v1 (`lib/features/shared/live/live_config.dart`; every field optional, an older server gets the recommended defaults): codec, weak-network mode (`adaptive` / `audio_first`), camera caps per role, screen fps / bitrate, DTX / RED, cameras off at join, pause hidden video, recording mode / engine — set by the super admin in `lib/features/admin/live_settings/` (`GET/PUT /api/v1/admin/live-settings`, kill switch `admin.live_settings`, D-089). Publishing follows `live_media_plan.dart`; receiving is the pure `live_quality_governor.dart` (drops remote video to LOW on the first bad sample, climbs one tier per 12 s of good; `live_net_pill.dart` shows it). Draw every track with `LiveVideoView` (`widgets/live_video_view.dart`, D-092), never livekit's `VideoTrackRenderer` directly: that renderer swallows the stage's taps and re-attaches on every build; the self-view box / circle is `live_self_view.dart`. Room clocks tick a `ValueNotifier`, not a room-wide `setState`. One presenter at a time (screen OR board) is decided by `live_share_arbiter.dart`. Annotation over a share (`annotation/`, D-079 / D-083) and the whiteboard (`whiteboard/`, D-087, page formats D-093; a continuous page grows sideways when a stroke is held at a side edge, x −1.5..2.5 with the column at 0..1 and `bv: 3` once anything lies outside it, D-107) are vector items on LiveKit data topics (`annot`, `board`, `board.laser`), never a video track, except the 2 fps `whiteboard` track published only for server recording (D-090). Their protocols carry `v` / `bv` and ignore unknown types so older apps never crash; sender identity comes from the LiveKit participant, never a payload field; topics are routed in `widgets/live_data_route.dart`. Pure, unit-tested: `annotation_controller.dart`, `board_controller.dart`, `board_protocol.dart`, `board_format.dart` (`test/org/board_*_test.dart`, `live_presence_test.dart`); layout `test/ui/whiteboard*_layout_test.dart`. Kill switches `live.annotation`, `live.whiteboard`, `live.share_requests`, `live.teacher_controls`, `live.room_lock`. Round 5: viewers see the presenter's camera over a share / board (`live_presenter_cam.dart`, `widgets/presenter_cam_box.dart`, D-094); the top row + full view (`widgets/live_top_row.dart`, D-095; since D-108 ONE line that also carries the board's title / page / Stop — the board draws no bar in the room — and folds what does not fit into ⋮; full view = the content alone, a tap slides the bars in over it, `widgets/live_focus_chrome.dart`, the board view-only there); the board's hand tool + edge auto-scroll (`board_edge_scroll.dart`, D-096). **Recording (D-098, owner 2026-10-30): course sessions record on the TEACHER'S DEVICE** (`RECORDING_MODE=client`; the super admin's Live settings switch can pick `server` per new run, but production's egress must be upgraded first) — to keep recording CPU off the shared server during classes. The server still assembles the chunks after class (`../back/services/local_recorder.py`: three libx264 tiers, `FFMPEG_THREADS` = every core by default); making that cheap (measure, low priority, one tier, `-c copy` remux) is task 1 of `docs/live/NEXT_SESSION.md`.

**Free meetings, recording, full view (D-306).** A meeting opens with the recording stopped (`liveRecordsAtStart`, `lib/features/shared/live/live_recording_layout.dart`); the web recording draws the room from `recordingLayout` (room.dart "D-306" block: `_syncRecordingScene` on every re-sort, the board pushed into a canvas source; compositor commands `setLayout` / `addCanvas`); Android mixes the other people's voices into the recording (`android/.../RemoteAudioMix.kt`, reflection on the fork's playback callback); full view is edge to edge with immersive bars and free rotation on phones (`liveFullViewSystemUi`, `BoardTurnHint`), and touch screens get the big scrollbar thumb (`BoardRailLook.touch`). Tests: `test/org/live_recording_layout_test.dart`, `test/ui/live_recording_d306_layout_test.dart`.
